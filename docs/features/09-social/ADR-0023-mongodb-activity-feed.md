# ADR-0023 — MongoDB TTL Collection for Activity Feed

## Status

Accepted

## Context

The activity feed stores event records generated by user actions (games won/lost/drawn, puzzles solved, achievements). These records have three key characteristics:

1. **Write-heavy at peak:** Game completions and puzzle solves generate feed entries continuously. At 11M users with frequent play, this is a high-insert workload.
2. **Short-lived:** Entries older than 30 days are irrelevant and must be purged. A long-running cleanup cron job on PostgreSQL can cause lock contention.
3. **Append-only with no updates:** Once written, a feed entry is never updated.
4. **Denormalized for read performance:** Actor username is stored inline to avoid JOINs on every feed page load.
5. **Queried by set of actor IDs + cursor pagination:** The query pattern is `actorId IN [friendIds] AND _id < cursor ORDER BY _id DESC`.

Options considered:

**Option A — PostgreSQL table with cron cleanup:** Add an `activity_feed` table to PostgreSQL. TTL via a scheduled `DELETE WHERE created_at < NOW() - INTERVAL '30 days'`. Pros: single database. Cons: high-volume inserts compete with game/user write traffic on the same PostgreSQL instance; DELETE-based cleanup causes table bloat and requires `VACUUM`; schema changes require migrations.

**Option B — PostgreSQL with partitioning:** Partition the `activity_feed` table by month and `DROP` old partitions. Pros: fast partition drops. Cons: significant operational complexity; partition management is a maintenance burden; still shares Postgres I/O with critical game data.

**Option C — MongoDB with TTL index (chosen):** Store feed entries in a dedicated MongoDB collection `activity_feed`. MongoDB's TTL index automatically deletes documents when `createdAt` exceeds `expireAfterSeconds: 2592000` (30 days). No cron job, no table bloat, no VACUUM needed. MongoDB's document model accommodates the `metadata` field (variable shape per `ActivityType`) without a schema migration. The project already uses MongoDB for other unstructured data.

**Option D — Redis sorted set:** Store feed entries as JSON-encoded strings in a per-user sorted set, scored by timestamp. Pros: very fast reads. Cons: high memory cost for storing full activity payloads; no built-in TTL per entry (only per key); unbounded growth if not purged; data loss risk on Redis eviction under memory pressure. Not appropriate for durable feed storage.

**Option E — Event streaming (Kafka/BullMQ) with read model:** Publish game/puzzle events to a message queue; a consumer builds the feed read model. Pros: decouples producers from the feed store; allows fan-out at scale. Cons: substantial additional infrastructure; over-engineered for current scale. ARCHITECTURE.md notes BullMQ can be wired in later if throughput requires it.

## Decision

Use **Option C: MongoDB TTL collection**. The collection schema is:

```typescript
{
  _id: ObjectId,             // used as pagination cursor (ObjectId encodes creation time)
  actorId: string,           // userId — indexed
  actorUsername: string,     // denormalized for display
  type: ActivityType,        // 'GAME_WON' | 'GAME_LOST' | ... (enum stored as string)
  targetId: string | null,   // gameId, puzzleId, achievementId
  targetName: string | null, // human-readable target name
  metadata: object,          // variable shape per ActivityType
  createdAt: Date,           // TTL index field
}
```

Indexes:
- `{ createdAt: 1 }, { expireAfterSeconds: 2592000 }` — TTL index for automatic 30-day purge
- `{ actorId: 1, createdAt: -1 }` — compound index for feed queries (actorId IN [...] sorted by recent first, maps to `_id` descending)

`_id` (ObjectId) is used as the pagination cursor rather than `createdAt`. ObjectIds are time-ordered within a second and guaranteed unique, making them a stable and gap-free cursor. The feed query uses `_id: { $lt: cursorObjectId }` for cursor-based pagination.

`ActivityFeedService.publish()` is called fire-and-forget from `GameService` and `PuzzlesService`. Errors are caught and logged but not re-thrown to avoid disrupting the game completion flow.

## Consequences

**Positive:**
- TTL index handles cleanup automatically — no cron jobs, no `VACUUM`, no manual partition drops.
- MongoDB's flexible document model accommodates the variable `metadata` field across `ActivityType` variants without schema migrations.
- Feed write traffic is isolated to MongoDB, keeping PostgreSQL I/O available for game state and user data.
- ObjectId-based cursor pagination is efficient, stable, and does not require an explicit `createdAt` index for pagination.
- Write performance: MongoDB's append-only insert pattern with no contention from reads on the same collection is well-suited to the write pattern.

**Negative:**
- Introduces MongoDB as a second database technology. Teams must operate and monitor two database systems. Mitigated by MongoDB Atlas managed hosting.
- Actor username is denormalized. If a user changes their username, old feed entries display the old username. Accepted trade-off for read performance; a background update job can be added later.
- Feed entries are not retroactively removed when a friendship ends. If Alice and Bob unfriend, Bob's old entries no longer appear in Alice's feed (because `getFriendIds` excludes them), but the documents still exist in MongoDB. This is correct behavior and requires no cleanup.
- The `$in` query across potentially hundreds of friend IDs could be slow at extreme scale. Mitigated by the `{ actorId: 1, createdAt: -1 }` index and by the practical cap on friend counts. A future architecture could pre-compute per-user feed lists (fan-out-on-write) if needed.
